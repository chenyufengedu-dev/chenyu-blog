# B2：让结论真正成为一份方案

> 配套方案：[`specs/2026-08-15-cyber-office-experience-roadmap.md`](../specs/2026-08-15-cyber-office-experience-roadmap.md)
> 前置任务：[`2026-08-16-cyber-office-speech-bubbles.md`](./2026-08-16-cyber-office-speech-bubbles.md)（B1 气泡化）

## 产品原则

**一场不出方案的讨论，在体验上是失败的。**

起承转合里，结论就是那个"合"。没有它，前面所有的争论都变成没有结局的戏，用户看完只会有一种"所以呢？"的落空感。这跟它是不是工具无关，**纯粹是叙事完整性的要求**。

## 现在的问题：模板是写死的

`buildSummarySystemPrompt` 里这一行：

```
"输出必须包含：核心结论、文章大纲、下一步行动。"
```

**「文章大纲」是硬编码的**——它假设每场讨论都是在定一篇文章的选题。于是你问「如何让单细胞空间转录组可视化更好」，它也会硬塞一份文章大纲给你。这就是结论读起来像套模板的根源。

还有一句 `"文字要适合放在 Chenyu 的个人技术博客作品集中"` —— 用户问自己的问题时，凭什么产出要为你的博客服务？这句会让结论莫名其妙地自我指涉。

## 改成什么

一份**跟议题无关、但永远成立**的方案结构：

| 段落 | 作用 |
|---|---|
| 结论 | 一两句**直接回答用户的问题**，不铺垫 |
| 为什么 | 2–3 条关键判断，**注明是谁的视角** —— 让人看出结论是从讨论里长出来的 |
| 争议点 | 讨论中的分歧与取舍 —— **这是多 Agent 讨论区别于单次问答的证据** |
| 怎么做 | 3–5 条可执行的具体步骤 |
| 先做这一件 | 最小起点，降低"看完不知道从哪下手"的落空感 |

- [x] **Step 1: `src/lib/cyber-office/prompts.ts` —— 重写总结 Agent 的人设**

把 `buildSummarySystemPrompt` **整个函数**替换为：

```ts
export function buildSummarySystemPrompt(): string {
  return [
    "你是 Cyber Office 的总结 Agent。",
    "几位专家刚围绕用户的问题开完一场圆桌会议，现在由你收口，产出一份能直接用的方案。",
    "",
    "严格按以下 Markdown 结构输出，标题原样保留：",
    "",
    "## 结论",
    "一到两句话直接回答用户的问题。不要铺垫，不要复述问题。",
    "",
    "## 为什么",
    "2-3 条关键判断。每条注明是哪位专家的视角，例如「（生信研究员）」。",
    "",
    "## 争议点",
    "讨论中出现的分歧与取舍，写清楚各方在争什么、代价是什么。",
    "若确实没有分歧，写「本次讨论未出现明显分歧」，不要编造。",
    "",
    "## 怎么做",
    "3-5 条具体可执行的步骤，要有对象和动作，不要写「加强」「优化」这类空话。",
    "",
    "## 先做这一件",
    "从上面挑出成本最低、能最快验证方向的那一步，一句话说清。",
    "",
    // 有输出长度上限，写太长会被从中间硬截断。宁可精炼，也必须五段都写完。
    "全文控制在 700 字以内，五个部分都要写完，不要写到一半停下。",
    "结论必须建立在上面的讨论记录之上，不要引入讨论里没出现过的新主张。",
  ].join("\n");
}
```

> 三个关键变化：
> ① **结构与议题无关**——不再假设用户在写文章；
> ② **要求标注观点来源**——让人看出结论是从讨论中长出来的，而不是模型自己另写一篇；
> ③ **单列争议点**——这是"多个 Agent 讨论"区别于"问一次模型"的最直接证据。

## 一个要留意的张力

B1 为了塞进气泡把发言压到了 60 字，这让**给总结 Agent 的素材变薄了**（6 轮 × 60 字 ≈ 400 字）。

结构化的提示词能在一定程度上补偿——它逼模型从有限素材里提炼而不是灌水。但如果实测下来结论确实空，**优先加轮数（`maxTurns`）而不是加每句字数**：多几次交锋既能喂饱总结，又不会撑破气泡。
