# C1：内容层真人感（角色人设 + 允许交锋）

> 配套方案：[`specs/2026-08-15-cyber-office-experience-roadmap.md`](../specs/2026-08-15-cyber-office-experience-roadmap.md)
>
> **要解决的问题**：「发言内容像 AI、每个人说话调调都差不多、各说各话没有交锋」。
> **成本**：纯提示词，两个文件，零技术风险。**这是当前性价比最高的一步。**

## 病根有两条，都在提示词里

### ① 人设太薄

现在每个角色的全部人设只有一句：

```
你的职责：把握目标与用户价值。
```

五个角色本质上是**同一个模型戴了五顶帽子**，帽子上只写了职务。这么薄的设定，就算换成五个不同厂商的模型也一样会雷同。

### ② 有一句话明令禁止争论

```ts
"你只能从自己的角色视角发言。"
```

这句的字面意思是"别管别人说了什么，只管说你自己那摊"。**它是"轮流表态、像课堂发言"的直接原因**——不是模型不会吵架，是我们不许它吵。

- [ ] **Step 2: `src/lib/cyber-office/prompts.ts` —— 重写角色提示词**

把 `buildRoleSystemPrompt` **整个函数**替换为：

```ts
export function buildRoleSystemPrompt(roleId: RoleId): string {
  const role = getRole(roleId);
  const persona = ROLE_PERSONA[roleId];

  return [
    `你是${role.name}。`,
    `你的职责：${role.title}。`,
    persona ?? "",
    "",
    "你正在参加一场圆桌讨论，像真人开会一样。",
    // ⚠️ 原来这里写的是"你只能从自己的角色视角发言"——那句话等于禁止争论，
    //    是"各说各话、轮流表态"的根源。现在反过来，明确鼓励交锋。
    "如果你不同意前面某个人的说法，直接点他的名字反驳，说清楚你为什么不同意。",
    "如果你认同，也不要复读一遍，而是补上他没说到的那一层。",
    "",
    "发言控制在 60 个中文字符以内，一到两句话讲完。",
    "要有判断和理由，别只抛结论，也别面面俱到。",
    "不要铺垫、不要客套、不要总结上文。",
    "不要自称 AI，不要输出 Markdown 标题。",
  ]
    .filter(Boolean)
    .join("\n");
}
```

- [ ] **Step 5: `src/lib/cyber-office/deepseek-client.ts` —— 提高角色发言的温度**

温度（temperature）决定模型的"随机性"。数值低时它总挑最保险的说法，五个角色就会趋同；调高之后措辞和视角会明显散开。

在 `stream` 方法里，把：

```ts
        temperature: 0.5,
```

替换为：

```ts
        // 角色发言要有个性，温度调高让措辞和视角散开。
        // 主持人的 complete 保持低温（0.4）——它要输出稳定的 JSON，不能发挥。
        temperature: 0.9,
```

> 只改 `stream`（角色发言），**不要动 `complete` 的 0.4**——主持人和总结需要稳定输出，调高会让 JSON 格式出错。

- [ ] **Step 7: 实机验证**

> ⚠️ 这一步**必须跑实时会议**。「看一场演示」是写死的样本，改提示词对它没有任何影响。

```bash
npm run dev
```

跑一场实时会议，用一个容易有分歧的问题，比如：

> 个人技术博客到底该不该做成花哨的交互式网站？

**验收标准（本任务的核心指标）**：

1. **遮住名字，能不能猜出是谁说的？** —— 这是最硬的标准。产品经理该像产品经理，审稿人该咄咄逼人。
2. 有没有出现**指名道姓的反驳**（"我不同意前端刚才说的…"）？
3. 主持人的串场是不是**变短了**（20 字以内），不再长篇大论？
4. 有没有出现**同一个人被连续点名追问**的情况？
5. 结论区的「争议点」那一段，是不是终于**有真实内容**了（而不是"未出现明显分歧"）？

> 第 5 条是个连带效果：B2 的结论结构里有「争议点」一段，但之前根本没有分歧可写。C1 之后它才有素材。

## 如果做完还是觉得雷同

说明确实撞到了"单一模型"的天花板。下一步的性价比顺序是：

1. **同厂不同模型**（零新增基建）：让审稿人用 `deepseek-reasoner`（推理型，天生更爱挑逻辑漏洞），其他人用 `deepseek-chat`。同一个 API key、同一套限流。
   - 实现上很轻：`orchestrator.ts` 里的 `ChatModel` 本来就是接口，把 `createDeepSeekChatModel()` 改成"按角色返回不同 model"即可，**编排逻辑一行不动**。
2. **多厂商混用**：效果更彻底，但要多个 key、多份账单、多套限流。除非确有需要，否则不划算。

**先跑 C1，再决定要不要上这两条。** 别用最贵的手段解决最便宜的问题。
